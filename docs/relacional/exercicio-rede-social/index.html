EXERCÍCIO RESOLVIDO · PASSO A PASSO

Desenhar uma rede social

Partimos de requisitos escritos em linguagem corrente. Em cada etapa fazemos uma pergunta, analisamos alternativas e só depois revelamos uma solução relacional.

O sistema deve permitir

  • Registar utilizadores.
  • Publicar vários posts por utilizador.
  • Comentar posts.
  • Fazer “like” num post, no máximo uma vez.
  • Criar grupos com vários membros e um moderador.
00

Começar pelo que existe no problema

Antes de criar tabelas, sublinhamos substantivos, ações e regras. Ainda não decidimos chaves nem tipos de dados.

Pergunta para a turma: quais destes elementos têm dados próprios e quais parecem apenas relações entre elementos?
01

Primeira entidade: UTILIZADOR

A tabela deve identificar uma pessoa da rede e impedir emails repetidos.

Que campos são necessários?

Um nome chega para identificar um utilizador?

UTILIZADOR

utilizador_idPK
nomeNOT NULL
emailUNIQUE · NOT NULL

Não. Duas pessoas podem ter o mesmo nome. Criamos um ID estável e conservamos o email como chave alternativa.

02

Como guardar os posts?

Cada utilizador pode publicar um número desconhecido de posts. Vejamos quatro soluções plausíveis antes de escolher.

Faça uma pausa antes de revelar: peça aos alunos para desenharem a sua primeira proposta.
ALTERNATIVA A

Adicionar post e data a UTILIZADOR

UTILIZADOR(id, nome, email, post, data)
Só permite um post por utilizador. O segundo post obriga a substituir o primeiro.
ALTERNATIVA B

Criar post1, post2, post3…

UTILIZADOR(..., post1, data1, post2, data2)
Cria grupos repetidos, muitos NULL e um limite artificial. E quando surgir o post 101?
ALTERNATIVA C

Repetir a linha do utilizador

Ana · ana@… · “Bom dia”
Ana · ana@… · “Segundo post”
Duplica nome e email. Alterar o email da Ana exige encontrar e corrigir todas as linhas.
ALTERNATIVA D

Separar POST, mas sem uma PK

POST(texto, data, utilizador_id)
Dois posts podem ter o mesmo texto e instante. Comentários e likes não têm uma identidade simples para referenciar.

A solução normalizada

Uma entidade repetível merece a sua própria tabela. Cada post guarda apenas a identidade do autor.

UTILIZADOR

utilizador_idPK
nome
email
1 ─ N

POST

post_idPK
autor_idFK → UTILIZADOR
texto
publicado_em
Leitura: um utilizador pode publicar muitos posts; cada post tem um autor. A FK autor_id impede posts associados a utilizadores inexistentes.

03

Comentários: duas relações numa tabela

Um comentário pertence a um post e é escrito por um utilizador. Portanto, precisa de duas chaves estrangeiras.

Que informação deve ser repetida no comentário?

UTILIZADOR

utilizador_idPK

POST

post_idPK
autor_idFK

COMENTÁRIO

comentario_idPK
autor_idFK → UTILIZADOR
post_idFK → POST
texto
publicado_em

Não copiamos o nome do autor nem o texto do post. Guardamos as chaves e obtemos os restantes dados por junção.

04

LIKE não é uma entidade comum

É sobretudo uma relação muitos-para-muitos: vários utilizadores podem gostar de vários posts.

Como impedir que a mesma pessoa faça like duas vezes no mesmo post?

LIKE_POST

utilizador_idPK · FK → UTILIZADOR
post_idPK · FK → POST
criado_em

A PK composta (utilizador_id, post_id) torna cada par único. As duas FKs recusam likes de utilizadores ou para posts inexistentes.

(101, 501) ✓
(102, 501) ✓
→
(101, 501) repetido ✕
(101, 999) post inexistente ✕
05

Grupos, membros e moderador

Um grupo tem muitos utilizadores e cada utilizador pode pertencer a vários grupos. Além disso, cada grupo tem um moderador.

Guardar seis colunas membro1…membro6?

Voltaria a criar um limite fixo e grupos repetidos. A pertença deve ser uma tabela associativa.

GRUPO

grupo_idPK
nome

MEMBRO_GRUPO

grupo_idPK · FK
utilizador_idPK · FK

MODERADOR_GRUPO

grupo_idPK · FK
utilizador_idFK
Regra subtil: uma FK simples para UTILIZADOR garante que o moderador existe, mas não garante que pertence ao grupo. Para garantir ambas as condições, o par (grupo_id, utilizador_id) de MODERADOR_GRUPO deve referenciar o mesmo par em MEMBRO_GRUPO. Como grupo_id é a PK de MODERADOR_GRUPO, existe no máximo um moderador por grupo.

Modelo final

UTILIZADORIdentidade das pessoas.
POSTUm autor; muitos posts.
COMENTÁRIORelaciona autor e post.
LIKE_POSTRelação N–N com PK composta.
GRUPOIdentidade do grupo.
MEMBRO/MODERADORPertença e papel controlados.
Fecho da aula: cada nova tabela surgiu para representar uma entidade repetível ou uma relação com regras próprias. As chaves não foram escolhidas apenas para “não repetir”: permitem referenciar, navegar e proteger a coerência.
