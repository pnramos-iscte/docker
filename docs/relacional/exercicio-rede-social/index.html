EXERCÍCIO RESOLVIDO · PASSO A PASSO

Desenhar uma rede social

Partimos de requisitos escritos em linguagem corrente. Em cada etapa fazemos uma pergunta, analisamos alternativas e só depois revelamos uma solução relacional.

O sistema deve permitir

  • Registar utilizadores.
  • Publicar vários posts por utilizador.
  • Comentar posts.
  • Fazer “like” num post, no máximo uma vez.
  • Criar grupos com vários membros e um moderador.

01

Primeira entidade: UTILIZADOR

A tabela deve identificar uma pessoa da rede e impedir emails repetidos.

Que campos são necessários?

Um nome chega para identificar um utilizador?

UTILIZADOR

utilizador_idPK
nomeNOT NULL
emailUNIQUE · NOT NULL

Não. Duas pessoas podem ter o mesmo nome. Criamos um ID estável e conservamos o email como chave alternativa.

Na segunda linha não sabemos quem publicou. Esta não é uma decisão técnica; é uma regra do sistema. Se a resposta for “não”, autor_id deve ser NOT NULL. Se for “sim”, pode aceitar NULL.

O sistema deve aceitar a segunda linha, isto é, posts sem autor identificado?

03

Comentários: duas relações numa tabela

Um comentário pertence a um post e é escrito por um utilizador. Portanto, precisa de duas chaves estrangeiras.

Um utilizador pode comentar o mesmo post mais do que uma vez?

comentárioautor_idpost_idhora
Concordo!10150110:05
Acrescento uma ideia…10150110:12

Se escolhermos (autor_id, post_id) como PK, a segunda linha é recusada. Isso pode ser intencional — um único comentário editável por pessoa — ou pode contrariar o requisito.

A base de dados deve aceitar as duas linhas, permitindo ao mesmo utilizador acrescentar outro comentário ao mesmo post?

Que informação deve ser repetida no comentário?

Solução mostrada: como admitimos vários comentários do mesmo utilizador no mesmo post, usamos comentario_id como PK. Se o requisito limitasse a um comentário, (autor_id, post_id) poderia ser a PK composta.

Como sabemos que uma pessoa não gostou de um post?

Sabemos que o utilizador 101 fez like no post 501. Se não existir uma linha para o utilizador 102, sabemos apenas que não fez like. Não sabemos se não gostou, se não viu o post ou se preferiu não reagir.

A ausência continua a significar “não reagiu”. O valor DISLIKE passa a afirmar explicitamente que não gostou. A PK composta permite uma única reação atual de cada utilizador a cada post.

05

Grupos, membros e moderador

Um grupo tem muitos utilizadores e cada utilizador pode pertencer a vários grupos. Além disso, cada grupo tem um moderador.

Guardar seis colunas membro1…membro6?

Voltaria a criar um limite fixo e grupos repetidos. A pertença deve ser uma tabela associativa.

GRUPO

grupo_idPK
nome

MEMBRO_GRUPO

grupo_idPK · FK
utilizador_idPK · FK

MODERADOR_GRUPO

grupo_idPK · FK
utilizador_idFK
Regra subtil: uma FK simples para UTILIZADOR garante que o moderador existe, mas não garante que pertence ao grupo. Para garantir ambas as condições, o par (grupo_id, utilizador_id) de MODERADOR_GRUPO deve referenciar o mesmo par em MEMBRO_GRUPO. Como grupo_id é a PK de MODERADOR_GRUPO, existe no máximo um moderador por grupo.
