Views
sem mistério

Uma view dá um nome a uma consulta. Pode apresentar apenas uma visão dos dados, simplificar comandos posteriores e limitar aquilo que cada utilizador consegue consultar ou alterar.

Começar ↓Descarregar exemplos SQL
CREATE VIEW vw_utilizador_pais AS
SELECT u.utilizador_id, u.nome,
       p.nome AS pais
FROM utilizador AS u
LEFT JOIN pais AS p
  ON p.pais_id = u.pais_id;

SELECT *

01

O que é uma view?

Uma view é uma tabela virtual definida por uma consulta. Para quem a usa, parece uma tabela; por baixo, o SGBD consulta as tabelas originais.

Tabelas reais
utilizador + pais
→
Consulta guardada
CREATE VIEW
→
Tabela virtual
vw_utilizador_pais
Visão

Mostrar apenas o necessário

Escolher colunas, filtrar linhas ou mudar nomes para apresentar os dados de forma adequada a um utilizador.

Reutilização

Dar nome a uma consulta difícil

Escrever uma junção ou agregação uma vez e reutilizá-la em consultas muito mais pequenas.

Acesso

Conceder permissões sobre a view

Permitir acesso ao resultado sem conceder automaticamente acesso direto a todas as tabelas e colunas de origem.

Uma view normal não guarda uma segunda cópia das linhas. Guarda a definição da consulta. Quando fazemos SELECT à view, os dados atuais são obtidos das tabelas de origem. Uma materialized view é outro conceito e não existe como funcionalidade nativa equivalente no MySQL.
CREATE VIEW vw_utilizador_pais AS
SELECT u.utilizador_id,
       u.nome,
       u.estado,
       p.nome AS pais
FROM utilizador AS u
LEFT JOIN pais AS p
  ON p.pais_id = u.pais_id;

Criar e consultar

CREATE VIEW nome AS consulta guarda a consulta com um nome.

Depois podemos usar vw_utilizador_pais em SELECT, WHERE, JOIN e outras operações como se fosse uma tabela.

SHOW CREATE VIEW vw_utilizador_pais; mostra a definição guardada.

02

Quando uma view simplifica mesmo

As views úteis escondem complexidade relevante. Uma view que apenas faz SELECT * FROM tabela raramente ajuda.

Exemplo 1 · Uma junção usada muitas vezes

-- Sem a view: repetir em cada relatório
SELECT u.nome, p.nome AS pais
FROM utilizador AS u
LEFT JOIN pais AS p
  ON p.pais_id = u.pais_id
WHERE u.estado = 'ativo'
  AND (p.nome = 'Brasil'
       OR p.nome IS NULL);
-- Com a view já criada
SELECT nome, pais
FROM vw_utilizador_pais
WHERE estado = 'ativo'
  AND (pais = 'Brasil'
       OR pais IS NULL);
A pergunta fica separada da forma de ligar as tabelas
A view resolve a associação entre utilizador e país. A consulta posterior concentra-se apenas no filtro pretendido.

Exemplo 2 · Uma agregação que passa a poder ser consultada

CREATE VIEW vw_estatisticas_autor AS
SELECT u.utilizador_id,
       u.nome,
       COUNT(p.post_id) AS total_posts,
       COALESCE(SUM(p.gostos), 0) AS total_gostos,
       COALESCE(AVG(p.gostos), 0) AS media_gostos
FROM utilizador AS u
LEFT JOIN post AS p
  ON p.utilizador_id = u.utilizador_id
GROUP BY u.utilizador_id, u.nome;

Um resumo reutilizável

A view resolve de uma vez o LEFT JOIN, o agrupamento e três agregações. Inclui autores sem posts porque começa em utilizador.

Outras consultas podem agora filtrar, ordenar ou juntar este resumo sem repetir a lógica.

Uma consulta posterior muito menor
SELECT nome, total_gostos FROM vw_estatisticas_autor WHERE total_posts >= 2 ORDER BY total_gostos DESC;

Exemplo 3 · Construir uma view sobre outra

CREATE VIEW vw_autores_relevantes AS
SELECT utilizador_id, nome,
       total_posts, total_gostos
FROM vw_estatisticas_autor
WHERE total_posts >= 2
   OR total_gostos >= 20;

Camadas com significado

A primeira view define como calcular estatísticas. A segunda define o que significa “autor relevante”.

Esta separação ajuda a manter regras usadas em vários relatórios, desde que não se crie uma cadeia tão longa que esconda completamente a origem dos dados.

03

Podemos escrever numa view?

Por vezes. Quando uma view identifica sem ambiguidade uma linha de uma única tabela base, o MySQL pode encaminhar a alteração. Quando a view calcula, agrupa ou combina resultados, deixa normalmente de ser atualizável.

Definição da viewSELECTINSERT/UPDATE/DELETERazão
Uma tabela, sem cálculosSimNormalmente simCada linha da view corresponde claramente a uma linha base.
Filtro WHERESimPode serWITH CHECK OPTION controla se a alteração pode sair do filtro.
JOINSimLimitadoA alteração não pode modificar ambiguamente várias tabelas; DELETE numa join view não é permitido pelo MySQL.
GROUP BY, agregações, DISTINCT, HAVINGSimNãoUma linha resume ou funde várias linhas de origem.
UNION/UNION ALLSimNãoO SGBD não consegue escolher inequivocamente o ramo a alterar.

Uma view simples e atualizável

CREATE VIEW vw_utilizadores_ativos AS
SELECT utilizador_id, nome,
       email, pais_id, estado, reputacao
FROM utilizador
WHERE estado = 'ativo'
WITH CHECK OPTION;

UPDATE vw_utilizadores_ativos
SET reputacao = 60
WHERE utilizador_id = 102;

O UPDATE chega à tabela base

A view usa apenas utilizador, e cada linha mantém o seu identificador. Alterar a reputação de 102 pela view altera a linha 102 da tabela utilizador.

Não existe uma cópia independente dentro da view.

Efeito
A reputação de Bruno passa a 60 tanto em utilizador como quando consultamos a view.

WITH CHECK OPTION impede que a linha desapareça

UPDATE vw_utilizadores_ativos
SET estado = 'inativo'
WHERE utilizador_id = 102;

A alteração seria possível sem a verificação

estado pertence à view e à tabela base, portanto poderia ser alterado. Contudo, WITH CHECK OPTION recusa 'inativo', pois a linha deixaria de satisfazer o filtro da própria view.

Alteração recusada
A view só aceita resultados que continuem visíveis através da sua condição.
INSERT tem uma exigência adicional: a view tem de fornecer valores para todas as colunas obrigatórias da tabela base que não tenham valor por omissão. Se a view esconder uma coluna NOT NULL sem DEFAULT, o INSERT pode falhar.
04

Views como fronteira de acesso

Uma view pode expor apenas as colunas e linhas adequadas. Depois, o administrador concede privilégios sobre a view em vez de abrir diretamente a tabela base.

CREATE VIEW vw_diretorio_publico AS
SELECT utilizador_id, nome, pais_id
FROM utilizador
WHERE estado = 'ativo';

GRANT SELECT
ON tutorial_sql.vw_diretorio_publico
TO 'leitor'@'%';

O email fica escondido

O utilizador leitor consulta nomes e países dos utilizadores ativos, mas a view não lhe apresenta o email.

Isto só é uma barreira real se o mesmo utilizador não tiver também SELECT direto sobre utilizador.

Princípio do menor privilégio
Conceda apenas as operações necessárias: por exemplo, SELECT sobre a view, sem SELECT sobre a tabela base.

SQL SECURITY DEFINER

A view verifica o acesso às tabelas usando, em geral, os privilégios do seu definidor. É a opção por omissão no MySQL.

SQL SECURITY INVOKER

A execução usa os privilégios de quem invoca a view. Esse utilizador precisa de acesso às fontes necessárias.

Não é anonimização automática

Combinações de colunas, filtros fracos ou outras permissões podem permitir inferir informação. A view deve ser desenhada e testada como uma interface de dados.

Manutenção: use CREATE OR REPLACE VIEW para substituir a definição e DROP VIEW nome para a remover. Remover uma view não remove as tabelas nem as linhas de origem.
05

Exercícios que obrigam a usar views

Em cada exercício, a solução deve criar pelo menos uma view e usá-la numa consulta posterior. Não basta escrever uma única consulta equivalente.

Diretório sem dados pessoais

Crie uma view com o identificador, nome e país dos utilizadores ativos, sem expor email nem reputação. Depois use a view para listar apenas Portugal, ordenado pelo nome. Escreva ainda o GRANT que permite ao utilizador consulta ler a view, mas não a tabela base.

Crie a view com utilizador LEFT JOIN pais e filtro por estado. A consulta seguinte filtra pais = 'Portugal'. O privilégio deve ser atribuído apenas sobre tutorial_sql.nome_da_view.

Catálogo editável e CHECK OPTION

Crie uma view dos utilizadores ativos com as colunas necessárias para alterar nome, email e reputação. Demonstre um UPDATE permitido. Depois tente transformar um utilizador em inativo através da view e explique como WITH CHECK OPTION deve impedir a operação.

Inclua estado na view para tornar possível tentar alterá-lo. Termine a definição com WITH CHECK OPTION. A mudança para inativo viola WHERE estado = 'ativo'.

Painel completo de autores

Crie uma view que devolva todos os utilizadores, incluindo os que não publicaram, com número de posts, total de gostos, média de gostos e data do último post. Use depois essa view para obter autores com total de gostos superior à média do total de gostos de todos os autores.

Use utilizador LEFT JOIN post, agrupe por utilizador e aplique COUNT, SUM, AVG e MAX. Na consulta posterior, compare total_gostos com (SELECT AVG(total_gostos) FROM nome_da_view).

Países com atividade acima da média

Primeiro crie uma view com o total de posts e gostos por país, incluindo países sem utilizadores ou sem posts. Depois use essa view para listar os países cujo total de posts é superior à média entre países. Explique por que razão são necessários LEFT JOIN sucessivos.

Comece em pais, faça LEFT JOIN utilizador e depois LEFT JOIN post. Agrupe pela PK e pelo nome do país. A subconsulta que calcula a média deve consultar a view já criada.

Autores acima da média do próprio país

Crie uma primeira view com a média de reputação por país. Crie uma segunda view que associe cada utilizador à média do respetivo país. Use a segunda view para mostrar quem tem reputação superior à média do seu país. Decida o que fazer aos utilizadores sem país e justifique.

A primeira view agrupa utilizador por pais_id. A segunda liga utilizador a essa view pela igualdade de pais_id. Um INNER JOIN exclui quem tem país nulo; um LEFT JOIN conserva-o, mas a comparação com média nula não será verdadeira.

Autores sem qualquer publicação

Crie uma view apenas com identificadores dos autores presentes em post. Use obrigatoriamente essa view e NOT EXISTS para encontrar utilizadores sem publicações. Escreva também uma solução com NOT IN e explique o risco que apareceria se a view pudesse conter NULL.

NOT EXISTS correlaciona a view com o utilizador exterior. NOT IN pode deixar de devolver linhas se a lista interior contiver NULL; elimine nulos na view ou prefira NOT EXISTS.

Vista mensal reutilizada duas vezes

Crie uma view com ano, mês, quantidade de posts, autores distintos e total de gostos. Use-a numa consulta que compare cada mês com o mês mais ativo e calcule a diferença de posts. Não repita a agregação sobre post na consulta final.

A view agrupa por YEAR(publicado_em) e MONTH(publicado_em). A consulta final pode consultar a view e usar uma subconsulta SELECT MAX(total_posts) FROM view.

Uma view deliberadamente não atualizável

Crie uma view que classifique os autores como sem posts, ocasional ou frequente, com base no número de posts. Tente atualizar diretamente a classificação e explique o erro. Proponha a operação correta sobre as tabelas base para um autor passar de ocasional a frequente.

A classificação usa COUNT, GROUP BY e CASE, logo não corresponde a uma coluna armazenada. Não se atualiza o rótulo: inserem-se novos posts na tabela post; a view recalcula a classificação.

Desafio de permissões por curso

Imagine que utilizador passa a ter curso. Crie views separadas para LEI e LIGE que permitam atualizar email apenas a alunos do respetivo curso. Use WITH CHECK OPTION, proponha os GRANT necessários e demonstre que um gestor de LEI não consegue mover um aluno para LIGE através da sua view.

Cada view filtra um curso e inclui as colunas editáveis e curso. O gestor recebe SELECT, UPDATE(email) sobre a sua view. Se também pudesse atualizar curso, o CHECK OPTION impediria a linha de sair do filtro.

Quatro perguntas antes de criar uma view

Que complexidade esconde?

Junções, agregações ou uma regra reutilizada.

Que dados expõe?

Linhas e colunas adequadas ao público.

Deve aceitar escrita?

Verifique a correspondência com linhas base e use CHECK OPTION.

Quem pode usá-la?

Conceda apenas os privilégios estritamente necessários.
