SQL desde o princípio

SQL significa Structured Query Language, em português, Linguagem de Consulta Estruturada. Aprenda a fazer perguntas a uma base de dados. Cada consulta parte da anterior, para que perceba o que cada palavra acrescenta ao resultado.

1970

De onde veio o SQL?

O modelo relacional e a linguagem SQL nasceram no mesmo programa de investigação da IBM, mas não exatamente ao mesmo tempo nem pelas mesmas pessoas.

1970

O modelo relacional

Edgar F. Codd publicou o modelo relacional: dados organizados em relações e operações com fundamento matemático.

1974

SEQUEL, antecessor do SQL

Donald Chamberlin e Raymond Boyce apresentaram a linguagem SEQUEL para consultar bases de dados relacionais. O nome evoluiu depois para SQL.

DeclarativaDizemos o que queremos obter. O SGBD escolhe como encontrar os dados.
Base matemáticaAs operações inspiram-se na álgebra e no cálculo relacionais, ligados à teoria dos conjuntos.
Para dados relacionaisSQL nasceu para operar sobre relações. Muitos produtos alargaram a linguagem a outros tipos de dados.
Standard comumA família ISO/IEC 9075 define SQL. MySQL, PostgreSQL, SQL Server e Oracle partilham o núcleo, mas têm extensões e diferenças.
Não é compilada como CO SGBD recebe cada instrução, analisa-a, cria um plano de execução e executa-o. Algumas instruções podem ser preparadas e reutilizadas.
Formatação livreEspaços e mudanças de linha quase nunca mudam o significado. As palavras reservadas não precisam de maiúsculas, embora as usemos para ler melhor.
A ideia essencial: SELECT nome FROM utilizador WHERE reputacao > 60 descreve o resultado. Não manda abrir um ficheiro, percorrer um índice ou comparar linhas numa ordem concreta. O otimizador do SGBD decide esse percurso.

Fontes históricas: artigo de Codd, 1970; artigo SEQUEL de Chamberlin e Boyce, 1974. Standard: ISO, modelo da linguagem SQL.

A primeira consulta

SELECT indica as colunas que quer ver. FROM indica a tabela onde os dados estão.

Filtrar linhas com WHERE

WHERE contém uma expressão lógica: para cada linha, o resultado tem de ser verdadeiro ou falso. Apenas as linhas que produzem verdadeiro seguem para o resultado.

A regra mental: imagine que o SGBD coloca uma linha de cada vez à frente da condição. Nessa linha, reputacao >= 60 pode ser avaliada imediatamente, sem consultar outra linha.

Rigor adicional: quando uma comparação envolve NULL, SQL pode produzir um terceiro resultado lógico, UNKNOWN. Tal como as linhas falsas, as linhas com resultado desconhecido não passam o filtro.

Uma operação que tenta “ver” várias linhas

A linha atual tem uma reputação, mas não contém a média da tabela. AVG(reputacao) precisa de observar o conjunto inteiro.

Por isso, uma função de agregação não pode ser usada diretamente no WHERE. Mais adiante poderá calcular a média numa subconsulta.

05

Compreender GROUP BY

GROUP BY junta numa só unidade todas as linhas que têm o mesmo valor. Depois, cada função de agregação trabalha separadamente sobre as linhas de cada grupo.

Uma imagem mental útil: pense numa tabela temporária conceptual. Cada linha dessa nova tabela representa um grupo e contém, como se fosse uma “caixa”, o conjunto de linhas da tabela original que pertence ao grupo. O SGBD não tem de criar fisicamente esta tabela; é uma forma de compreender a operação.

O problema que queremos resolver

Imagine que quer saber quantos utilizadores existem em cada estado. Não pretende uma linha por utilizador: pretende uma linha por estado, com o respetivo total.

O resultado que queremos obter
estadototal de utilizadores
ativo5
inativo1
Para chegar aqui, o SQL tem primeiro de reunir todas as linhas com estado = 'ativo' e todas as linhas com estado = 'inativo'.

Existem agora duas linhas conceptuais porque existem dois valores de estado. Dentro de cada linha conceptual está um conjunto de linhas originais.

3. As funções resumem cada conjunto

SELECT estado,
       COUNT(*) AS total,
       AVG(reputacao) AS media
FROM utilizador
GROUP BY estado;

Uma linha por grupo

COUNT(*) conta as linhas que estão dentro de cada “caixa”. AVG(reputacao) calcula a média usando apenas as reputações dessa caixa.

O resultado tem duas linhas, não seis, porque o agrupamento criou dois grupos.

Porque existem regras no SELECT?

SELECT estado, nome, COUNT(*)
FROM utilizador
GROUP BY estado;

Esta consulta está errada

No grupo ativo existem cinco nomes. Que nome deveria o SGBD escrever na única linha desse grupo: Ana, Bruno, Diogo, Eva ou Fábio?

estado é igual em todo o grupo, portanto pode ser mostrado. COUNT(*) resume o grupo. nome não faz nenhuma das duas coisas.

Erro com ONLY_FULL_GROUP_BY ativo
O MySQL indica que nome não pertence ao GROUP BY nem é calculado por uma função de agregação.
Regra prática e respetiva razão: quando existe uma função de agregação no SELECT, todos os restantes campos do SELECT devem aparecer no GROUP BY. Assim, esses campos têm um único valor bem definido em cada grupo. Uma exceção avançada ocorre quando o SGBD consegue provar uma dependência funcional, mas não precisa dela nesta fase.

HAVING: o WHERE da tabela de grupos

SELECT pais_id, COUNT(*) AS total
FROM utilizador
GROUP BY pais_id;

Primeiro são criados os grupos

O resultado tem um grupo para cada pais_id, incluindo um grupo para NULL. Ainda não foi aplicado nenhum filtro aos grupos.

Depois, HAVING filtra os grupos

Pense no HAVING como o WHERE da tabela conceptual de grupos. Aqui conserva apenas as “caixas” que contêm mais do que uma linha original.

WHERE filtraria utilizadores antes de formar os grupos. HAVING filtra os grupos já formados.

A ordem das cláusulas

A consulta escreve-se numa ordem fixa. Pensar na ordem lógica ajuda a perceber o resultado.

1SELECT
2FROM / JOIN
3WHERE
4GROUP BY
5HAVING
6ORDER BY
Ordem lógica simplificada: o servidor começa por FROM, aplica WHERE, forma grupos, aplica HAVING, calcula o SELECT e ordena no fim.

Combinar tabelas

Antes de aprender JOIN, é importante perceber o que acontece quando se colocam duas tabelas no FROM e por que razão precisamos de relacionar a chave primária com a chave estrangeira.

       pais.nome AS pais

WHERE utilizador.pais_id = pais.pais_id;

3. Escrever a mesma associação com JOIN

SELECT u.nome,
       p.nome AS pais
FROM utilizador AS u
JOIN pais AS p
  ON p.pais_id = u.pais_id;

INNER JOIN

Esta consulta devolve o mesmo resultado da anterior. JOIN e INNER JOIN significam o mesmo.

A vantagem é a clareza: a condição que relaciona as tabelas fica em ON; o WHERE fica livre para condições que filtram linhas. Em consultas com várias tabelas, isto reduz esquecimentos, evita produtos cartesianos acidentais e torna a intenção muito mais fácil de ler.

Os prefixos u. e p. indicam a tabela de origem de cada coluna.

SELECT u.nome,
       p.nome AS pais
FROM utilizador AS u
LEFT JOIN pais AS p
  ON p.pais_id = u.pais_id;

LEFT JOIN: preservar a tabela da esquerda

O INNER JOIN devolve as linhas que encontraram correspondência. O LEFT JOIN pode ser entendido como a união entre:

1. o resultado do INNER JOIN;
2. as linhas da tabela da esquerda que não foram apanhadas por esse JOIN.

Nessas linhas adicionais, as colunas da tabela da direita ficam com NULL. Mais adiante veremos como construir esta mesma ideia usando explicitamente UNION.

Se trocássemos a ordem das tabelas, poderíamos preservar os utilizadores com um RIGHT JOIN:

FROM pais AS p RIGHT JOIN utilizador AS u ON p.pais_id = u.pais_id

Pergunta malandra

Se todas as chaves estrangeiras fossem obrigatórias, seria necessário usar LEFT JOIN?

Neste exemplo, normalmente não. Se utilizador.pais_id for NOT NULL e existir uma restrição de chave estrangeira válida, todos os utilizadores têm obrigatoriamente um país existente. Assim, o INNER JOIN já inclui todos os utilizadores e produz o mesmo resultado do LEFT JOIN.

Mas atenção: declarar apenas NOT NULL não basta. Isso impede a ausência de valor, mas só a restrição FOREIGN KEY garante que o valor corresponde realmente a uma linha da tabela pais.

Pergunta importante

Onde deve ficar a condição que liga as tabelas?

Em ON. Sem uma condição correta, pode obter combinações sem significado ou um número enorme de linhas.

Uma consulta dentro de outra

Uma subconsulta é uma consulta usada por outra consulta. Nas subconsultas correlacionadas, uma imagem mental útil é um ciclo for dentro de outro for.

A ideia dos dois ciclos: a consulta exterior escolhe uma linha de utilizador. Para essa linha, a consulta interior percorre linhas de post. Os dois ciclos têm de estar ligados: a consulta interior precisa de saber qual é o utilizador que está a ser tratado pela consulta exterior. Em SQL, essa ligação aparece numa condição como p.utilizador_id = u.utilizador_id.
-- Imagem mental; não é código SQL
FOR cada u IN utilizador          -- ciclo exterior
  FOR cada p IN post              -- ciclo interior
    IF p.utilizador_id = u.utilizador_id
       foi encontrada uma correspondência
linha exterioro ciclo interior procuraencontrou?decisão
Ana · 101post com utilizador_id = 1011001 e 1002fica
Bruno · 102post com utilizador_id = 1021003fica
Diogo · 104post com utilizador_id = 104nenhumnão fica

Esta é uma explicação conceptual. O otimizador do SGBD pode executar a consulta de uma forma mais eficiente, sem realizar literalmente estes ciclos.

1. IN: comparar com uma lista produzida pela subconsulta

SELECT u.nome
FROM utilizador AS u
WHERE u.utilizador_id IN (
  SELECT p.utilizador_id
  FROM post AS p
);

Quem escreveu pelo menos um post?

A consulta interior produz a lista (101, 101, 102, 103, 106). Para cada utilizador, a consulta exterior pergunta se o seu identificador pertence a essa lista.

Esta subconsulta não precisa de consultar a linha exterior: pode ser compreendida começando pela consulta interior.

Resultado com IN
nome
Ana Costa
Bruno Lima
Carla Sousa
Fábio Alves

2. EXISTS: fazer a mesma pergunta com dois ciclos ligados

SELECT u.nome
FROM utilizador AS u
WHERE EXISTS (
  SELECT 1
  FROM post AS p
  WHERE p.utilizador_id = u.utilizador_id
);

O mesmo resultado com EXISTS

Para cada linha u, a subconsulta procura uma linha p ligada ao utilizador atual. A igualdade é a “ponte” entre os dois ciclos.

EXISTS pergunta apenas se foi encontrada pelo menos uma linha. Por isso, o SELECT 1 não significa que queremos mostrar o número 1: o valor selecionado no interior não interessa.

Resultado com EXISTS: igual ao de IN
nome
Ana Costa
Bruno Lima
Carla Sousa
Fábio Alves
IN ou EXISTS? Neste problema, ambos exprimem corretamente a pergunta. IN é natural quando queremos comparar um valor com uma lista. EXISTS é especialmente claro quando queremos confirmar a existência de uma linha que satisfaz uma ou várias condições relacionadas com a linha exterior.

3. Quando uma comparação IN simples já não chega

Queremos agora utilizadores que tenham escrito um post no mesmo ano em que se registaram. É necessário verificar simultaneamente dois valores: o identificador do utilizador e o ano.

SELECT u.nome
FROM utilizador AS u
WHERE u.utilizador_id IN (
  SELECT p.utilizador_id,
         YEAR(p.publicado_em)
  FROM post AS p
);

Erro: um valor contra duas colunas

À esquerda de IN existe apenas u.utilizador_id. A subconsulta devolve duas colunas. O SQL não sabe comparar um valor com pares de valores.

Erro devolvido pelo MySQL
ERROR 1241 (21000): Operand should contain 1 column(s)
SELECT u.nome
FROM utilizador AS u
WHERE EXISTS (
  SELECT 1
  FROM post AS p
  WHERE p.utilizador_id = u.utilizador_id
    AND YEAR(p.publicado_em) = YEAR(u.data_registo)
);

EXISTS permite ligar vários campos

A subconsulta sabe qual é a linha exterior através do sinónimo u. Pode, por isso, comparar o autor e o ano na mesma procura.

O primeiro for está na linha u; o segundo percorre p e usa os valores dessa linha u nas duas condições.

nome

Bruno Lima

Nota para mais tarde: alguns SGBD, incluindo o MySQL, também aceitam pares de colunas com a sintaxe (campo1, campo2) IN (SELECT campo1, campo2 ...). Contudo, um IN simples compara apenas uma expressão, e EXISTS torna normalmente mais visíveis as várias condições de ligação.

4. Uma subconsulta sobre a própria tabela

SELECT u1.nome, u1.reputacao
FROM utilizador AS u1
WHERE EXISTS (
  SELECT 1
  FROM utilizador AS u2
  WHERE u2.pais_id = u1.pais_id
    AND u2.reputacao > u1.reputacao
);

Quem tem alguém do mesmo país com reputação superior?

A tabela utilizador participa duas vezes. Precisamos, por isso, de lhe dar dois sinónimos: u1 é o utilizador exterior e u2 é o possível outro utilizador.

Para cada u1, o ciclo interior percorre novamente a tabela como u2. As condições ligam os dois: mesmo país e reputação superior.

Juntar resultados com UNION

UNION coloca as linhas de uma consulta por baixo das linhas de outra. As consultas precisam do mesmo número de colunas e de tipos compatíveis.

SELECT nome, 'utilizador' AS origem
FROM utilizador
UNION
SELECT nome, 'país' AS origem
FROM pais;

UNION ou UNION ALL

UNION elimina linhas duplicadas. UNION ALL mantém todas as linhas e costuma ser mais rápido.

Reconstruir o LEFT JOIN com UNION

Na secção anterior vimos que um LEFT JOIN equivale conceptualmente às linhas encontradas pelo INNER JOIN, mais as linhas da tabela esquerda que não encontraram correspondência. Podemos agora escrever literalmente essas duas partes.

-- Parte 1: combinações em que FK = PK
SELECT u.nome, p.nome AS pais
FROM utilizador AS u, pais AS p
WHERE u.pais_id = p.pais_id

UNION ALL

-- Parte 2: utilizadores sem país correspondente
SELECT u.nome, NULL AS pais
FROM utilizador AS u
WHERE u.pais_id IS NULL
   OR u.pais_id NOT IN (
     SELECT p.pais_id
     FROM pais AS p
   );

As duas partes do LEFT JOIN

A primeira consulta começa pelo produto cartesiano e usa u.pais_id = p.pais_id para conservar as associações corretas.

A segunda usa NOT IN para encontrar chaves que não existem em pais. Acrescentamos IS NULL porque uma comparação NULL NOT IN (...) não é verdadeira: produz UNKNOWN.

UNION ALL coloca as linhas não associadas por baixo das linhas associadas.

Porque continuamos a preferir LEFT JOIN? A versão com UNION ALL ajuda a compreender a operação, mas repete trabalho e é mais longa. LEFT JOIN exprime diretamente a intenção e deixa o SGBD escolher um plano de execução eficiente.
Não confundir: JOIN acrescenta colunas ao relacionar tabelas. UNION acrescenta linhas ao combinar resultados compatíveis.

Guardar o resultado

No phpMyAdmin, execute a consulta e use a opção Exportar junto ao resultado. O formato CSV abre facilmente numa folha de cálculo.

  1. Execute a consulta e confirme que as colunas e linhas estão corretas.
  2. Na zona do resultado, escolha Exportar.
  3. Escolha CSV, confirme o separador e descarregue o ficheiro.
Boa prática: dê nomes claros às colunas com AS antes de exportar. Esses nomes serão os cabeçalhos do ficheiro.
